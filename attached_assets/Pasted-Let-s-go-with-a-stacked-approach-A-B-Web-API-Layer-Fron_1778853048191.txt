Let's go with a **stacked approach: A + B (Web API Layer + Frontend SPA)**.
Building the engine is one thing, but having a clean, functional interface to actually *interact* with the data transforms this from a CLI tool into a proper research platform. By stacking Axum with a modern frontend, we can implement the real-time search and the parallel viewer you've got on the roadmap.
Since we're moving to **v0.2**, I’ll scaffold the project structure. This setup includes an Axum backend and a React/Vite frontend. I'll also ensure we use **port 0** for the API to keep things flexible and avoid local conflicts.
### Project Scaffolding (v0.2)
### 1. Project Directory Structure
We’ll use a monorepo-style layout to keep the Rust backend and the frontend logic close together.

### 2. Backend API (Axum)
This provides the REST endpoints for searching and Strong's lookups.
cat << 'EOF' > biblica-v0.2/backend/src/main.rs
use axum::{routing::get, Router};
use std::net::SocketAddr;
#[tokio::main]
async fn main() {
let app = Router::new()
.route("/api/search", get(|| async { "Search results" }))
.route("/api/strongs/:id", get(|id: axum::extract::Path<String>| async move {
format!("Lookup for Strong's: {}", id)
}));
// Using port 0 for dynamic assignment
let addr = SocketAddr::from(([127, 0, 0, 1], 0));
let listener = tokio::net::TcpListener::bind(addr).await.unwrap();
let local_addr = listener.local_addr().unwrap();
println!("Backend listening on {}", local_addr);
axum::serve(listener, app).await.unwrap();
}
EOF
